* Runtime recognition

[[file:../src/aw2_lab/lifecycle.py][lifecycle.py]] now recognizes:

- =BATTLE_POWER=: process =0x0849D77C= under the verified battle callbacks.
  The process spans the observed quote, activation presentation, and effects
  for both regular and Super Power. The active-power byte alone does not
  identify this phase: it becomes 1 or 2 and stays active after input returns.
- =BATTLE_COMBAT=: either resolver =0x0849FEF8= (animated) or =0x0849FFB0=
  (without the full battle animation), with a human Fire parent
  =0x0849A9F8= or verified computer controller mode 1/state 14, under battle
  or animation callbacks. CPU attacks lack the human Fire parent.
- =BATTLE_COMPUTER_TURN=: mode 1/state 14 with battle callbacks, no active
  screen processes, zero locks/gates, and input substate zero. Unknown overlays
  or other CPU substates remain unresolved. This phase blocks live decoding.

Known result processes retain precedence over these associations. Missing or
conflicting evidence does not establish human control. The full supported
decoder subset still requires =BATTLE_PLAYER_TURN= and all structure checks.

Original-ROM checks corroborate both resolver literals at =0x0802C56C= and
=0x0802C570=, the Fire parent's wait for the non-animated resolver at
=0x0849AA18=, the two visual branches at =0x08041D14/0x08041D3C=, and
the Power parent literal at =0x0803964C=. Mode/state checks build on the
earlier verified controller dispatch, rather than equating a CPU portrait
with a controller state.

* Real save and resume

** Saving and cold boot
The newly supplied checkpoint is archived by SHA-256
=e8c05cecb640a87a6b49bc5ec5bbee9e8c5c091c707c052cde4afdd50560afd3=.
It starts at frame 10926, day 4, player 2, with Super available. A separate
branch opens Save, completes its text, selects Yes, and confirms the save.
An A press while text is appearing can finish the text without selecting Yes;
the captured confirmation and resulting SRAM change are part of the evidence.

The completed save checkpoint is frame 11301. Extracting its unmodified native
mGBA =gbAx= savedata extension (tag 2) produces the 65,536-byte game save:
=64c187930e67fb79ed646262c255e4e0064cf952141f1599609ccf1fc2826669=.
The game subsequently loads that save through its own Continue command; the
RAM is not patched to simulate a resumed battle.

The pinned headless startup path does not explicitly autoload SRAM. Adjacent
save files alone did not make the initial Continue attempt work. The successful
research session uses a temporary Lua bootstrap to call =emu:loadSaveFile= on
an isolated save copy, reset, and load the repository bridge. The savedata
extension in the resulting cold-boot checkpoint matches the save hash above.
This bootstrap is an external research helper; normal launcher SRAM loading
and windowed-mode parity are not implemented or certified here.

Older retained save-dialogue checkpoints contained uninitialized Flash headers.
Those experiments, wrong menu selections, and attempts without explicitly loaded
SRAM are excluded from successful resume evidence. All emulator ROM/save/XDG
writes use temporary copies, leaving the supplied files untouched.

* Computer combat and animation settings

The retained four-player battle supplies three CPU opponents. With full
animations, the trace includes all three CPU turns, battles without a human
Fire parent, unit damage/destruction, and the next red human turn. There are
no human-turn classifications within the CPU portion.

Settings are changed through Options, without memory writes:
- Visual C describes itself as viewing player battle animations only. Its
  three-CPU-turn trace contains 104 observations with the alternate resolver
  and no animation-engine callbacks, before normal human control returns.
- No Visual describes itself as no animation. The human Tank attack uses
  =0x0849FFB0=; there is no full-screen animation-engine switch. Cleanup
  still passes through states 16 and 13 with input substate 4 before returning
  to substate zero. A temporary occupied zero-health record also fails unit
  validation before the destroyed unit's type clears.

Separate attempts holding L from attack confirmation or pulsing B/Start during
an animation did not skip that animation. They are negative controls, not a
verified shortcut. The confirmed skip coverage is the game-provided Visual C
and No Visual settings; other shortcuts or animation modes remain unverified.

* Powers, dialogues, and input probes

Regular Power and Super both retain the Power parent through their effects.
The regular trace ends with active byte 1, and the supplied Super trace with
active byte 2. Neither value prevents decoding once the presentation finishes
and normal controller/structure checks pass. The two activations are separate
branches, so their frame numbers are not directly comparable durations.

Save confirmation, overwrite confirmation, partially displayed text, Options,
and Yield confirmation are blocked even when all supported arrays are valid.
Several have no active screen-pool process and retain controller state 13;
their nonzero controller lock prevents live decoding. The additional confirmed
Yield branch removes the yielding army and starts CPU play. It is not a newly
verified final defeat presentation or an automatic elimination dialogue.

Seven independent Right-versus-neutral probes contain 140 controller snapshots.
They reject the Right pulse at resume frame 3304, regular-Power frame 129001,
Super frame 11621, and CPU frame 14795. Right moves the cursor only in the
corresponding normal-control checkpoints at 3305, 129003, and 11623. A universal
command-readiness flag is still outside the claim.
