#+TITLE: AW2 Battle Lifecycle Research

Verified observations, candidate lifecycle signals, counterexamples, and remaining
checks for Milestone 2. General methods are in [[file:AW2-RESEARCH-NOTES.org][AW2 research notes]]; battle
field layouts are in [[file:AW2-MAP-RESEARCH.org][map/property research]]. Keep ROMs, save states, screenshots,
and memory artifacts outside the repository and Nix store.

Confirming Rules starts the battle automatically. The fade and day banner are
battle-entry animations; there is no additional Ready screen or confirmation.
Memory-field validity and whether the UI accepts a command are separate research
questions, not extra gameplay steps. The latest [[*Finding: Results, save-progress exit, and powers][result and power comparison]]
extends the initial observations below through victory/defeat, the save-progress
prompt, and return to map selection.

* Finding: Startup, title, Versus setup, and battle entry

** Claim and status
- Status: partial lifecycle verification. High confidence in the screen
  associations and counterexamples observed below; a universal positive
  memory-only lifecycle classifier is unresolved.

** Verified structures and bounded screen associations
All multi-byte values below are unsigned little-endian integers. Match this
exact ROM profile before using any addresses or script identifiers.

| Address/rule | Interpretation | Type and bounds | Corroboration |
|--------------+----------------+-----------------+---------------|
| =LE32(0x0801CB38)= | Screen-process pool base, =0x0200D610= | ROM literal =u32 LE= | Original search routine =0x0801CB28= |
| =0x0200D610 + 0x6C*n= | Process script identifier | =u32 LE=, n=0..31, zero means no script | Original search advances 0x6C and bounds index at 0x1F |
| =0x030040D0= | Engine callback A | =u32 LE=, Thumb function pointer | Setter =0x080366D0=, getter =0x080366E8= |
| =0x030040EC= | Engine callback B | =u32 LE=, Thumb function pointer | Setter =0x080366C4=, getter =0x080366DC= |

Read the 32-slot pool as a bounded 3,456-byte region. Check each slot's first
word; do not infer activity from leftover callbacks or payload bytes in a slot
whose script word is zero. Match known script values; unrecognized values have
no lifecycle meaning established here. Pool absence is not a positive battle
signal. No linked-list traversal or unbounded pointer following is needed for
these presence checks.

The two callback pairs, preserving their Thumb low bits, are:
- Screen engine: =(0x08036885, 0x080368E9)= in all seven non-battle source states.
- Battle engine: =(0x08036945, 0x080369BD)= in the active-battle source state,
  the battle-entry fade, turn-start sequence, battle menu, and save prompt.

Original =0x0803662C= installs the battle pair; =0x080366A4= installs the screen
pair through the setters above. This verifies engine selection, not battle/UI
  phase or input availability. Never execute or dereference these values as host pointers.

Every supplied state was sampled at restore, after 10 neutral frames, and after
60 total neutral frames. Callback pairs and the associated screen script remain
consistent in all 24 observations. Campaign and Versus highlights share the
same parent process; Teams and Rules also share their parent. A finer phase
decoder needs additional verified child state. The byte at =0x02017C76= is 0
in Teams and 2 in Rules, but remains 2 in battle; it is only a candidate setup
subphase lead, with no standalone validity interpretation.

** Decoder implications and unresolved work
- Reject battle decoding in recognized title/mode/map-selection/setup contexts.
  The screen-engine pair is a conservative exclusion signal for the observed
  Versus path. Unknown or conflicting signals must remain unknown.
- A matching battle-engine pair supports an engine-family observation. Classify
  battle entry, power activation, and known result sequences separately; it is
  not an unconditional ongoing-battle or command-availability flag. Validate
  individual fields in their observed phases. An animation does not by itself
  invalidate already initialized map data or introduce another confirmation.
- Keep map-data validity, lifecycle phase, and whether the UI accepts commands
  separate. These observations demonstrate that their transitions need not
  coincide, without establishing their complete validity intervals.
- Victory/defeat, post-result prompts, and retained map/day/property data after
  returning to menus were missing from this initial run. The later result finding
  supplies those observations for the tested two-army paths.
- Check Campaign, resumed battles, AI turns, combat, powers/dialogues, and more
  menu/transition paths before generalizing these associations. Verify windowed
  parity separately. The title timer can eventually enter other behavior; these
  neutral controls cover only the first 60 frames after each source state.

** Player-record fields verified for these observations
Let =P = LE32(0x08499598) = 0x02023284=, and =R(k) = P + 0x3C*k=.
The original routines use this 60-byte stride. Records k=1 and k=2 correspond
to the observed red and blue armies in these checkpoints. This does not resolve
army/player-slot reassignment or teams. Validate k within 1..4 and ensure the
record lies within EWRAM; the preceding k=0 record is not a player in this finding.

| Rule | Field | Type | Verification and limits |
|------+-------+------+-------------------------|
| =R(k)+0x14= | Defeated marker | =u16 LE= | Zero before loss, 15 for blue in the day-15 victory path, 1 for red in the day-1 defeat path |
| =R(k)+0x1E= | Active power status | =u8= | 0 inactive, 1 normal Power, 2 SUPER in the observed Andy cases |

Original =0x080266DC= reads the defeated halfword and treats nonzero as not
alive; it additionally requires a nonzero participation/control byte at offset
=0x1B=. Preserve the raw marker rather than assuming a one-byte Boolean. Its
observed values coincide with the defeat day, but a general defeat-date field
has not been separately established. The displayed result establishes red WIN
and blue LOSE for the victory path; the other path visibly establishes red's
defeat. Do not infer a universal winning-team algorithm from these samples.

Original =0x0804415C= checks the active-power byte for nonzero.
=0x08044144= copies the neighboring byte at offset =0x1F= into =0x1E=;
=0x08044178= clears =0x1E=. The adjacent byte can stay 1 or 2 when active
status is zero: red has =(0,1)= in state 5 and blue has =(0,2)= in state 4.
It must not be used as the active-power flag. Other player fields, power-meter
scaling/thresholds, and the adjacent byte's complete lifecycle remain unverified.
