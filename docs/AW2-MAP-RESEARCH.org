*** Verified fields and resolution rules
Read =LE16= and =LE32= as unsigned little-endian integers. Byte fields below
are unsigned; byte order does not apply to a single byte.

Let =B = LE32(0x08499590) = 0x0201E450= for this exact ROM profile. For a valid
zero-based coordinate, let =i = LE16(B + 0x417A + 2*y) + x=.

| Address/rule | Field | Size/type | Evidence and confidence |
|--------------+-------+-----------+-------------------------|
| =B + 0= | Map width | =u16 LE= | 16 in both states; right edge clamps at x=15; high |
| =B + 2= | Map height | =u16 LE= | 15 in both states; bottom edge clamps at y=14; high |
| =B + 0x417A + 2*y= | Row offset in cells | =u16 LE= | All 15 entries equal y*16 in both states; original code uses this lookup; high |
| =B + 0x0A22 + 2*i= | Graphical tile ID | =u16 LE= | 240 cells per map match decompressed original-ROM data; city capture changes the ID; high |
| =B + 0x1432 + i= | Terrain class and encoded owner | =u8= | Distinct terrain landmarks, both maps' buildings, and capture transition agree; high |
| =0x03003150 + 4*n + 0= | Property terrain/owner byte | =u8= | Every listed property matches the terrain grid; capture changes the matching entry; high |
| =0x03003150 + 4*n + 1= | Property x coordinate | =u8= | All 28/31 entries match zero-based map locations; high |
| =0x03003150 + 4*n + 2= | Property y coordinate | =u8= | All 28/31 entries match zero-based map locations; high |
| =U + 5=, bits 3..7 | Infantry's accumulated capture points | =u8 >> 3= | Wait gives 0; partial capture gives 10; completion resets to 0; original capture routine agrees; high within this experiment |

For the terrain/owner byte, =raw & 0x1F= gives the terrain class and =raw >> 5=
gives an owner code. Verified classes are plain =1=, mountain =3=, wood =4=,
road =5=, city =6=, sea =7=, HQ =8=, and base =14=. Observed owner codes are
=0= for neutral, =1= for red, and =2= for blue in these checkpoints. Mapping
these codes to player slots or army colors in other configurations is unresolved.
For example, neutral/red/blue cities are =0x06=, =0x26=, and =0x46=.

The capture field belongs to a unit record, not to the four-byte property entry.
During confirmed infantry selection/capture actions, =U = LE32(0x030040D8)=
was =0x02022690=. The original capture routine resolves this pointer through
the literal at =0x08091354= and uses the upper five bits at unit offset =5=.
This is accumulated progress; the city UI shows =20 - progress= in this test.
The lower three bits are not interpreted here.

*** Pointer handling, bounds, sentinels, and validity
- Select the exact supported ROM before using =B= or the other address rules.
  =B= comes from a 32-bit ROM literal, not an assumed host pointer. The original
  routines at =0x08009B38= and =0x08024058= corroborate unsigned row-offset and
  terrain reads; =0x080240B4= corroborates the halfword tile array.
- Validate =0 <= x < width= and =0 <= y < height= before reading the row offset;
  require =i < width*height=. Both observed arrays contain exactly 240 active
  cells, with no border cells in coordinate indexing. Read only the =height=
  active row offsets. Maximum dimensions/allocation capacity remain unresolved;
  this finding validates only the observed 16-by-15 geometry.
- The property list has four-byte stride. Stop when its first byte is =0xFF=;
  do not interpret the remaining bytes of that sentinel as a property. Sentinels
  occur at =0x030031C0= and =0x030031CC= in the initial states. Original-ROM
  enumeration/readers at =0x08021B48=, =0x08021CB4=, and =0x0800C608= bound
  indexes to =0..0x5B= (92 slots); cap traversal at 92 even without a sentinel.
  The original reader skips inactive entries with first byte zero; deletion and
  a full 92-slot list were not exercised at runtime.
- The property entry's fourth byte was zero throughout this experiment and
  remains unknown. Do not identify it as capture progress.
- The current-unit pointer can be stale: after the AI turn, it still referenced
  an AI infantry at =(8,13)= while the cursor was over the red infantry. Resolve
  it only in an independently confirmed unit-selection/action context, check
  alignment and that the required record bytes lie inside EWRAM, and corroborate
  the unit's coordinates. General unit-table bounds/identity are future research.
- All interpretations assume a manually confirmed active battle. These fields
  do not yet provide a battle-lifecycle validity detector, and are not validated
  at title screens, menus, transitions, or in windowed-mode parity comparisons.
