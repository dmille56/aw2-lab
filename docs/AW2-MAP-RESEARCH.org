* IWRAM cursor coordinate pair

The two bytes at =0x03003140= are the map cursor's zero-based X and Y in
controlled Versus map observations: byte +0 is X and byte +1 is Y. The
five-map verification at =/tmp/aw2-map-research-five/verify.py= compares the
captured bytes directly with expected coordinates for 45 controlled cursor
samples. Right changes X, Down changes Y, and edge probes show both values
clamp to the map bounds. This establishes byte order and coordinate meaning
for those playable-map samples.

The field does not identify the active UI cursor in every phase. The startup,
title, mode, map-select, Teams, and Rules checkpoints retain =00 00=; the
first playable checkpoint has =01 09=. Restored command-menu, Options, Power,
save-progress, and Yield overlays retain map-coordinate pairs such as
=(01 07)=, =(04 08)=, and =(0A 05)=. Treat these as the last map cursor
coordinates, not as a menu-row or selected-command index. The map cursor is
visually present while the command menu is open, but the field alone does not
prove input readiness; lifecycle and controller checks still apply.

Static tracing is incomplete. An exact-address scan of the supported ROM
found no literal reference to =0x03003140=, which suggests code may calculate
the address from a nearby base or copy it indirectly. The matching decompilation
contains readers of =gUnknown_03003100= at =0x0802927C= and =0x08028E3E=;
those instructions read offsets 0 and 2 from that separate address and do not
establish reads or writes of =0x03003140=. Thus the runtime meaning and byte
order are verified, but the game's specific reader/writer routines and the
field's validity outside the tested Versus map surface remain unresolved. A
watchpoint or complete data-flow trace is needed before claiming ROM-level
cross-reference coverage.

*** Verified fields and resolution rules
Read =LE16= and =LE32= as unsigned little-endian integers. Byte fields below
are unsigned; byte order does not apply to a single byte.

Let =B = LE32(0x08499590) = 0x0201E450= for this exact ROM profile. For a valid
zero-based coordinate, let =i = LE16(B + 0x417A + 2*y) + x=.

| =B + 2= | Map height | =u16 LE= | 15 in both states; bottom edge clamps at y=14; high |

*** Static ROM trace: property record byte 3
- ROM: the supported US revision-0 image, SHA-256
  =ef3cc89273f9df88020f07751ea6306b25c39df01893822fe431550eedf9b134=.
- I traced the known direct references to =0x03003150= in the available AW2BHR
  Thumb disassembly. Property-list construction at =0x0800C574= and the rebuild
  path at =0x080219AC= write the terrain/owner byte and coordinates at offsets
  =0=, =1=, and =2=, then write =0xFF= to the next entry's offset =0= as the
  terminator. Property counting, filtering, coordinate lookup, and terrain
  synchronization paths at =0x0800C874=, =0x0800C8A0=, =0x0800C8D8=,
  =0x0800C608=, =0x08021CB4=, =0x08028660=, and =0x0803F990= read fields at
  offsets =0..2=; =0x0800C608= clears the matched entry's first byte in its
  editor path. No instruction in these located property-table paths reads or
  writes offset =3=.
- There is a separate scratch list at =gUnknown_084995A0= with eight-byte
  entries. The constructors at =0x0800C574= and =0x080219AC= explicitly zero
  byte =+3= in that scratch list. That is a different structure and does not
  identify the fourth byte of the four-byte property entries.
- Result: the fourth property byte remains semantically unknown; the traced
  code gives no evidence that game logic consumes it. This agrees with the
  supplied checkpoints, where every active fourth byte has been zero. The code
  evidence is limited to the functions represented in this partial disassembly;
  it does not prove that no other retail-ROM path accesses the byte. A broader
  binary-wide access audit or controlled nonzero-byte experiment would be needed
  to close that gap. Static trace does not alter the unresolved status.

For the terrain/owner byte, =raw & 0x1F= gives the terrain class and =raw >> 5=
gives an owner code. Verified classes are plain =1=, mountain =3=, wood =4=,
road =5=, city =6=, sea =7=, HQ =8=, and base =14=. Observed owner codes are
=0= for neutral, =1= for red, and =2= for blue in these checkpoints. Mapping
these codes to player slots or army colors in other configurations is unresolved.
For example, neutral/red/blue cities are =0x06=, =0x26=, and =0x46=.

The capture field belongs to a unit record, not to the four-byte property entry.
During confirmed infantry selection/capture actions, =U = LE32(0x030040D8)=
was =0x02022690=. The original capture routine resolves this pointer through
the literal at =0x08091354= and uses the upper five bits at unit offset =5=.
This is accumulated progress; the city UI shows =20 - progress= in this test.
Their meaning is unresolved; the comparison below checks whether they change
during a normal Infantry city capture.

*** User-confirmed capture rules
The user reports the following gameplay rules from direct play. These general
rules are recorded separately from the RAM-controlled cases below:
- Capturing a property requires 20 points. An Infantry or Mech adds points
  equal to its current HP when it completes a Capture action while on the
  property.
- If that unit moves or fires from the property, its accumulated capture
  points reset.
- Sami's Infantry and Mechs add 1.5 points per HP when capturing.
- While Sami's Super CO Power is active, her Infantry and Mechs can capture a
  city in one turn regardless of their current HP. The user reports this as a
  gameplay rule; the Super Power checkpoints below directly demonstrate
  one-turn captures by both unit types, but use full-HP units.

The controlled 4-HP Infantry Capture/Wait comparison independently agrees with
the reported normal rate: it records four added points. The supplied property
capture checkpoints also show partial progress in the unit record and zero
progress after completion. The five Sami checkpoints independently connect her
normal capture bonus to 15 progress points for full-HP Infantry and Mech. The
Super CO Power behavior is user-confirmed to work regardless of unit HP; the
separate two-city Sami checkpoint sequence above provides full-HP examples for
both unit types. The move/fire reset rule remains a user-confirmed gameplay
observation without an isolated RAM comparison.

*** Pointer handling, bounds, sentinels, and validity
- Select the exact supported ROM before using =B= or the other address rules.
  =B= comes from a 32-bit ROM literal, not an assumed host pointer. The original
  routines at =0x08009B38= and =0x08024058= corroborate unsigned row-offset and
  terrain reads; =0x080240B4= corroborates the halfword tile array.
- Validate =0 <= x < width= and =0 <= y < height= before reading the row offset;
  require =i < width*height=. Both observed arrays contain exactly 240 active
  cells, with no border cells in coordinate indexing. Read only the =height=
  active row offsets. Maximum dimensions/allocation capacity remain unresolved;
  this finding validates only the observed 16-by-15 geometry.
- The property list has four-byte stride. Stop when its first byte is =0xFF=;
  do not interpret the remaining bytes of that sentinel as a property. Sentinels
  occur at =0x030031C0= and =0x030031CC= in the initial states. Original-ROM
  enumeration/readers at =0x08021B48=, =0x08021CB4=, and =0x0800C608= bound
  indexes to =0..0x5B= (92 slots); cap traversal at 92 even without a sentinel.
  The original reader skips inactive entries whose first byte is zero. No
  internal zero-valued entries were observed in the active portion of these
  runtime tables. The user confirms that properties do not disappear during a
  battle, so battle-time deletion/reuse is not an appropriate test. Ring Islands
  has 85 active records followed by the sentinel and six zeroed slots.
- The property entry's fourth byte was zero throughout this experiment and
  remains unknown. Do not identify it as capture progress.
- The current-unit pointer can be stale: after the AI turn, it still referenced
  an AI infantry at =(8,13)= while the cursor was over the red infantry. Resolve

| Byte +1 bit | Mask | Established behavior |
|-------------+------+----------------------|
| 0 | =0x01= | Used this turn. Action completion sets it; unit cycling skips it; owning-turn reset clears it unless bit 3 is set. |

| 2 | =0x04= | Retain temporary logical occupancy while bit 1 is set. An existing logical entry with this bit set may be replaced by another unit at that coordinate. |
| 3 | =0x08= | Embarked passenger in the Load/Drop paths: Load sets it and Drop clears it. Owning-turn reset preserves bit 0 while it is set. |
| 4 | =0x10= | Carrier has cargo in the Load/Drop paths: Load sets it; Drop clears it when the compacted cargo list is empty. |
| 5 | =0x20= | Sub Dive sets it and Rise clears it; the map renderer uses it to select an alternate tile path. |
| 6 | =0x40= | On removal, records the unit's army in =0x030030F8=; verified with an injected flag. |
| 7 | =0x80= | On removal, records that army in =0x030030F8= only when no other active unit in the army has bit 7; verified with injected flags. |

*** ROM readers and writers
- =sub_080258CC= builds a logical lookup at =MAP_BASE+0x051A= and a visible
  lookup at =MAP_BASE+0x12=, using global unit indices at row-offset plus X.
  At =0x08025978..0x08025980= it skips a record when
  =(status & 0x06) == 0x02=. Thus bit 1 without bit 2 excludes it from both
  lookups; =0x06= retains logical occupancy. At
  =0x080259AE..0x080259B6= an existing logical occupant is replaceable only
  when that occupant has bit 2. At =0x080259C0..0x080259C8= any bit-1 unit
  is excluded from the visible lookup. Subsequent FoW/control filtering can
  also remove visible entries, so visible-table absence alone cannot identify
  bit 1.
- =sub_08025340= and =sub_08025378= respectively set and clear bit 1 for a
  global unit reference. Selection/action helper =sub_08035584= sets both
  bits 1/2 (=OR 0x06=) and associates the record with an action process.
  Cleanup =sub_08035828= clears both bits (=AND 0xF9=) on that process's
  unit record. =sub_080424FC= calls that cleanup before setting bit 0; if
  bit 3 is still set, it then restores bit 1. This explains the settled
  embarked value =0x0B= rather than treating =0x06= as an acted flag.
- Load =sub_08042864= resolves the carrier from the destination lookup. It
  fills carrier +7 if empty, otherwise +8, using the selected unit's global
  reference. At =0x080428BE..0x080428CC= it sets passenger bit 3 and carrier
  bit 4. The caller's action-completion path establishes used-this-turn and
  the passenger's exclusion from the visible and logical lookups.
- Drop =sub_080428F0= resolves passenger =carrier[7 + cargo_index]= against
  the global unit pool. At =0x08042914..0x08042922= it clears passenger bits
  3 and 1 (=AND 0xF7= then =AND 0xFD=), preserving bit 0. It writes the
  adjacent drop coordinates and clears that cargo link. When dropping index
  0 while +8 remains occupied, =0x08042954..0x08042966= shifts +8 into +7
  and clears +8. At =0x0804296C..0x08042978= it clears carrier bit 4 if +7
  is now empty. This establishes insertion/compaction statically; a runtime
  two-drop sequence confirms compaction and clearing the final link. In the
  observed UI sequence, passenger ref 3 from +7 drops before ref 4 from +8.
  The Transport Copter pair separately confirms clearing its single +7 link;
  see the Transport Copter finding.
- Turn reset =sub_08025EA0= checks bit 3 before clearing bit 0. Its skip
  now has a concrete cargo context: an embarked passenger retains its acted
  flag. Red-Lander checkpoints show two embarked passengers retain status
  =0x0B= from Red day 2 to Red day 3; see the owner-turn-reset finding.
- Fuel is byte +6's low seven bits, not the entire byte. The HUD read and
  arithmetic/initialization paths above confirm masking and preservation of
  bit 7 during fuel changes; Join propagates it. Its purpose and natural source
  remain unknown.
