#+TITLE: AW2 Battle Structure Validation

Conservative validation of the supported ROM's map geometry, property/feature
table, player records, and unit records. Layout evidence is in
[[file:AW2-MAP-RESEARCH.org][map/property research]] and [[file:AW2-LIFECYCLE-RESEARCH.org][lifecycle research]].

* Result and scope

- Date: 2026-10-25. The exact supported US revision-0 ROM was selected by
  SHA-256. Its map, unit, and player pointer literals and tile/terrain lookup
  are loaded by =load_battle_layout=; an unknown ROM or mismatching pointer is
  rejected before following addresses.
- [[file:../src/aw2_lab/state_validation.py][state_validation.py]] checks the supported structures and reports their
  raw consistency independently from whether they may be decoded as live.
  =can_decode_live= requires the verified =BATTLE_PLAYER_TURN= context and
  passing checks for all four structures. Menus, results, unknown contexts,
  transitions, locked menus, and computer turns are conservatively unavailable.
- Replay covered 297 archived full-RAM observations and 25 restored control
  checkpoints. The 170 archived human-turn observations all pass the supported
  checks, across 15 map geometries including 46 x 28, 39 x 30, and 33 x 35.
  None of the other 127 archived observations is exposed as a live battle.
- [[file:AW2-LIFECYCLE-RESEARCH.org::*Finding: combat animation and return to player control][Combat validation]] adds two animated attack traces and 19 restored snapshots.
  The Fire/resolver process pair blocks live decoding during combat; cleanup
  remains unavailable until the input substate resets. A transient occupied
  zero-health record also fails unit validation before its type is cleared.
  Only normal control resumes live availability. Archived result/dialogue
  signals retain precedence over combat processes.
- [[file:AW2-LIFECYCLE-COVERAGE.org][Additional lifecycle coverage]] checks 48 restored snapshots spanning real
  Versus resume, CPU combat, skipped/disabled animations, regular/Super Power,
  and save/yield dialogues. Nine normal human-control snapshots are available;
  all busy/menu/dialogue cases remain unavailable. The saved and resumed
  researched fields match, and all 297 earlier archive decisions are preserved.
- This certifies the researched subset in the tested contexts. It does not
  validate arbitrary mods, Campaign-only terrain, every transport, unknown
  record fields, or command readiness. There is no new state API endpoint or
  complete battle decoder in this change.

* Coherent captures and pointer rules

=capture_battle_snapshot= reads complete EWRAM and IWRAM in bounded 4-KiB
requests at a paused emulator frame. Every response and a final frame check
must agree; frame drift or incomplete data raises an error. Offline snapshots
must likewise come from a coherent capture; RAM bytes alone cannot prove their
own capture provenance.

| ROM literal | Expected GBA address | Rule |
|-------------+----------------------+------|
| =LE32(0x08499590)= | =0x0201E450= | Map structure |
| =LE32(0x08499594)= | =0x02022684= | Unit pool, including reserved slots |
| =LE32(0x08499598)= | =0x02023284= | Player-record base; slots 1..4 start after record zero |

The implementation bounds every read within captured GBA RAM and checks
halfword/word alignment. Dynamic dimensions, row offsets, property coordinates,
turn indices, and passenger indices are checked before dependent reads. No GBA
pointer is converted to a host pointer. The stale current-unit pointer at
=0x030040D8= is not used to identify a unit under the free cursor.

* Per-structure checks

** Map geometry

- Nonzero little-endian width/height at the map base.
- Supported retail envelope: width <=48, height <=39, area <=1,288. These are
  conservative support bounds based on the existing catalog/buffer research;
  they are not a new claim about the engine's theoretical limits.
- Every active row offset at =B+0x417A+2*y= equals =y*width=. A corrupt offset
  is rejected rather than followed into another array.
- Every graphical tile halfword at =B+0x0A22+2*i= fits the 1,024-byte ROM
  lookup and matches its terrain/owner byte at =B+0x1432+i=. The lookup loader
  at =0x080215D0= copies from =0x080C1BC4= through offset =0x3FF=.
- Currently supported graphical IDs are <=470 and terrain classes are
  =1..8,10..19=. Unsupported IDs/classes, including unverified Labs, yield
  =UNKNOWN=. Owner codes must be =0..4= and owned cells must be supported
  property/feature classes.

** Property and feature table

- Four-byte records at =0x03003150=, bounded to 92 slots. Stop on first byte
  =0xFF=; ignore the rest of that record and all trailing stale entries.
  Zero first-byte entries are skipped without interpreting their stale bytes.
  Missing termination within the bound makes the list unavailable.
- Every active coordinate is unique, inside the map, and matches the terrain
  grid's encoded type/owner. The list must cover the grid's supported feature
  cells exactly: City, HQ, Airport, Port, Base, unused silo, and spent silo.
- Non-neutral owners must refer to participating player records. Defeated
  players remain participating records; they are not confused with unused slots.
- The fourth property byte is deliberately uninterpreted. Capture progress is
  checked in the unit record. Silos remain features after launch.
- The 92-slot traversal bound is distinct from a proven maximum property count;
  the existing 88-property Royal Channel observation is supported. Larger-map
  and theoretical-capacity experiments remain deferred.

** Players and turn

- Read player slots =1..4= using the 60-byte stride. The participation/control
  byte at =+0x1B= determines whether a record is active; inactive records may
  retain arbitrary CO, team, and power bytes.
- Supported participating control types are 1 (human) and 2 (computer). Unknown
  controls or CO IDs outside =0..18= yield =UNKNOWN=.
- Slot/color ID =+0x1A= must match the slot, active power =+0x1E= must be
  =0..2=, and team =+0x2A= must be =0..3=.
- Day must be initialized, and the turn selector must identify a participating
  bounded slot. A recognized human turn whose selected player is marked
  defeated is unavailable for live decoding.

** Units and cargo

- The pool spans four =0x300=-byte address blocks, each with 64 physical
  12-byte records. Normal allocation starts at slot 1 and stops before slot 51;
  slot 0 and slots 51..63 are outside the supported allocator. A nonzero unit
  there yields =UNKNOWN= rather than being silently decoded.
- Original allocator =0x08025AEC= uses the current army's index offset, starts
  at offset+1, and loops while the index is below offset+=0x33=. Its record
  advance is =0x0C=. Thus the first usable record addresses remain
  =0x02022690,0x02022990,0x02022C90,0x02022F90=; starting a 64-record scan
  at one of those addresses would include the next block's reserved record.
- For an active record at =UNIT_BASE + 12*(64*army + slot)=, byte +0 is the
  unit-type ID. Controlled screenshots and movement/combat states match
  Infantry =0x01=, Mech =0x02=, APC =0x07=, and Md Tank =0x0B=; other supported
  IDs are enumerated by the ROM profile but have not all been individually
  matched to screenshots. There is no separate owner byte in this record:
  ownership is the containing army block, mapped to player slots/colors in the
  [[file:AW2-MAP-RESEARCH.org::*Finding: four-player army blocks, player slots, and colors][four-player comparison]].
- Bytes +2 and +3 are zero-based map X and Y coordinates. A controlled APC
  move changes record =0x02022804= from =(7,5)= to =(7,4)= while the screenshot
  shows the APC move one tile; other stationary units retain their coordinates.
  This confirms the candidate coordinate interpretation in the earlier
  movement snapshots.
- Halfword +4 packs health and ammo: bits 0..6 are internal health
  (=word & 0x7F=), observed from 1 to 100; bits 7..10 are ammunition
  (=(word >> 7) & 0x0F=). The damaged-infantry checkpoint pairs raw health
  =0x25= (37) with displayed 4 HP; combat checkpoints show it changing with
  damage. The Tank's =0x04E4= -> =0x0463= change on firing changes health
  100 -> 99 and ammo 9 -> 8. Independent Battle Copter state has ammo 6 in
  both the record and HUD. These examples verify the fields, not every
  internal-to-HUD health rounding case. See [[file:AW2-MAP-RESEARCH.org::*Finding: Tank firing and HUD ammunition comparison][the firing comparison]].
- Byte +6 bits 0..6 are fuel in the tested contexts: APC values =26= and =68=
  match the selected-unit HUD, and one controlled APC move reduces it from
  =68= to =67=.
  The supply comparison shows nearby units' byte +6 values rise, but does not
  establish all unit-specific limits or supply rules. The ROM HUD reader at
  =0x0802AEA2..0x0802AEAA= masks away bit 7; that bit remains unassigned.
- Byte +1 bit 0 is the used-this-turn flag in verified contexts. ROM action
  completion sets it, the unit-selection scan skips records with it set, and
  the turn-start reset clears it unless bit 3 is set. A controlled Wait
  comparison follows =0 -> 6= in the Wait menu, =1= after Wait resolves, and
  =0= at that army's next turn. ROM code ORs =0x06= into byte +1 in transient
  action UI paths. The lookup builder excludes bit-1 units from the visible
  lookup; bit 2 retains their logical occupancy and permits replacement of
  that temporary entry by another unit. The Load/Drop writers establish bit 3
  as embarked passenger and bit 4 as carrier with cargo in those paths. Load
  sets both flags on the corresponding records; Drop clears passenger bits
  3/1 and clears carrier bit 4 when its cargo list is empty. Thus the turn
  reset exception preserves an embarked passenger's acted flag. Reconstructed
  logical lookups match all 21 archived Wait/cargo gameplay captures. See
  [[file:AW2-MAP-RESEARCH.org::*Finding: unit status bits in map lookup and cargo routines][the status-bit trace]] and
  [[file:AW2-MAP-RESEARCH.org::*Finding: Wait status and start-of-turn upkeep][the Wait and upkeep comparison]]. Action bits 5..7 remain unassigned, and no
  flag alone establishes command readiness. Byte +5's upper five bits store
  capture progress in verified capture contexts; its low three bits carry
  ammo bits 8..10 of the packed halfword at +4. The controlled APC supply pair
  shows a Md Tank's ammo rising =2 -> 6= in these bits while fuel rises
  =45 -> 50=. IWRAM byte =0x03000799= is not a stable ammo value: it drifts
  from 0 to 11 over 30 neutral frames while Tank ammo stays at 8, and reads 4
  in the settled Battle Copter checkpoint that shows 6 ammo. It has no
  established ammo/cache role.
- A zero type byte marks an unused record, regardless of stale flags,
  coordinates, or health. Active records need a supported observed type, a
  participating owner block, coordinates inside the map, health =1..100= after
  masking with =0x7F=, and capture progress below 20 from byte +5 shifted right 3.
  ROM health reads mask with =0x7F=; rejecting raw values such as =0xE4= would
  incorrectly reject a full-health unit. Bits 7..10 are ammo, not a separate
  health flag.
- Supported APC/Lander links at +7/+8 are global unit indices, not universally
  small per-army slot numbers. Resolve =UNIT_BASE + 12*reference=; the high two
  bits identify the army block and the low six identify the slot. For example,
  blue reference 65 points to blue slot 1 at =0x02022990=. The earlier red
  slot-plus-one observations are the army-zero special case.
- Validate link range, own-army membership, target occupancy, self-links,
  duplicate parents, cycles, and APC capacity. Unsupported transport/link fields
  yield =UNKNOWN=. The original destruction routine at =0x08025D60= resolves
  both passenger bytes directly against the global unit base with stride 12.
- Do not require passenger/carrier coordinates to be equal. Across the archived
  data, 56 nonzero references cover both red and blue armies; 33 retain different
  passenger/carrier coordinates. All reference targets remain occupied in the
  matching army. Coordinate equality at the loading checkpoint is not a general
  invariant while the carrier moves. Nested transports are allowed if acyclic.

The guard permits a legitimate initial battle with no units, rather than using
nonempty unit records as an initialization test. Raw consistency cannot identify
which match retained bytes belong to. The conservative live interval begins at
the tested human-input state, and closes during unverified/busy contexts; this
does not imply the underlying map becomes physically invalid during every animation.

All 20 archived victory observations, the defeat observation, five result-summary
observations, three save-prompt observations, and five of six map-selection
observations pass all four raw checks. Every one remains unavailable as live
data. Two setup observations also retain a complete, consistent old battle.
These are direct counterexamples to treating structural plausibility as freshness.

* Runtime use

#+begin_src python
layout = load_battle_layout(rom_path)
snapshot = await capture_battle_snapshot(bridge, layout)
report = validate_battle_snapshot(snapshot)
report.require_live()  # Raises with lifecycle/structure reasons unless all checks pass.
# A supported decoder can now use this same immutable snapshot.
#+end_src

=report.available(BattleStructure.PROPERTIES)= checks the lifecycle and the
geometry/property/player dependencies; units likewise depend on geometry and
players. Player fields can be validated independently of malformed map geometry.
=VALID= means the implemented raw checks pass, =INVALID= means an observed
invariant fails, and =UNKNOWN= means coverage is missing or a dependency failed.
Neither unknown nor invalid data is available for live decoding.

The pure lifecycle classifier retains =battle_decode_safety=UNKNOWN= on a human
turn. The companion validation report supplies the guarded decision for the
supported fields. This is a library interface; wiring it into future state API
decoders is separate from validating these structures.

  sentinels, ownership, player indices, unit health/progress, global cargo links,
  inactive/stale records, cycles, frame drift, and truncated captures. They use
  no ROM or proprietary memory data. All 56 structure-validation cases and the
  full repository pre-commit checks passed.

  more transports/ownership scenarios, and allowing supported reads during AI
  turns or other busy phases. Normal animated combat is now checked; other
  attack/animation modes, CO-specific effects, and new elimination dialogues remain coverage gaps.
  Unverified fields and command availability remain
  outside the claim. Modded map sizes and theoretical table capacities stay deferred.
